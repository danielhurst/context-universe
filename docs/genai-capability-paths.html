Framework

GenAI Capability Paths

A strategic guide to AI implementation. This framework moves from strategic foundations (economic model and positioning) to capability design and execution. Organisations should establish their strategic foundation before designing their capability approach.

1. GenAI Capability Paths

Based on strategic foundation work, there are four distinct paths for capability and operating model design:

Path Description Strategic Signal Capability Approach Operating Model Typical Client
Platform Play Build AI as a shared enterprise capability that scales across the organisation Proprietary data assets, multiple BUs, economics support shared infrastructure Centralised GenAI platform: shared models, prompt libraries, governance, data pipelines Central AI platform team + embedded AI engineers in BUs. Federated model. Large enterprises, financial services, insurers with diverse product lines
Process Integration Play Embed AI deeply into existing workflows and systems to drive operational efficiency Moat is operational excellence, not unique data. Advantage from deep workflow embedding Orchestrate best-of-breed AI tools integrated into core systems (CRM, ERP, workflows) Process owners become AI orchestrators. Heavy change management. Upskill existing roles Operations-heavy businesses, BPO, logistics, back-office intensive orgs
Domain Moat Play Encode proprietary expertise and institutional knowledge into AI for defensible differentiation Deep domain expertise that is hard to replicate. Encode proprietary knowledge into AI Domain-specific fine-tuning, RAG over proprietary knowledge bases, expert-in-the-loop systems Domain experts paired with AI engineers. Knowledge capture as core process Professional services, specialised consultancies, niche B2B, regulated industries
Speed-to-Market Play Move fast, prove value, and build organisational AI muscle before worrying about long-term architecture No structural moat yet. Imperative is learning fast, proving value, building muscle Minimal platform. Managed services, API-first, low-code AI. Lightweight governance Small cross-functional AI squads. Centralised governance and vendor management only Mid-market, digitally immature but motivated, resource-constrained orgs

2. Execution Paths by Strategic Path

2.1 Platform Play — Execution Options

Execution Path Description Key Investments Timeline Risk Profile
Cloud-Native AI Platform Build on hyperscaler AI stack (Azure OpenAI, AWS Bedrock, GCP Vertex). Standardise on one ecosystem. Cloud architecture, MLOps, API management, centralised prompt engineering 6–12 months to MVP Medium. Vendor dependency but faster time to value
Multi-Model Orchestration Layer Abstract across multiple LLM providers. Build routing, evaluation, and fallback logic. Avoid lock-in. Model gateway, evaluation framework, cost optimisation layer, semantic routing 9–18 months Higher complexity but strategic flexibility
Data Platform First Prioritise data infrastructure before AI layer. Build unified data estate, then add GenAI capabilities on top. Data lakehouse, vector databases, data governance, retrieval infrastructure 12–24 months Lower AI risk, higher foundational value. Slower to visible wins

2.2 Process Integration Play — Execution Options

Execution Path Description Key Investments Timeline Risk Profile
Workflow Automation Stack Deploy AI-augmented automation across core workflows. Integrate Copilots into existing tools (M365, Salesforce, ServiceNow) Copilot licensing, workflow redesign, integration development, change management 3–6 months per workflow Low technical risk. High change management effort
Intelligent Document Processing Focus on document-heavy processes: intake, extraction, classification, routing. High-volume, measurable ROI. IDP platform, OCR/NLP integration, exception handling workflows, human review loops 4–9 months Proven pattern. ROI clear. Limited to document use cases
AI-Augmented Decision Points Embed AI recommendations at key human decision points in processes. Keep human in loop but accelerate decisions. Decision support UIs, recommendation engines, audit trails, feedback loops 6–12 months Balances automation with control. Requires trust-building

2.3 Domain Moat Play — Execution Options

Execution Path Description Key Investments Timeline Risk Profile
Knowledge Graph + RAG Build structured knowledge graph from institutional expertise. Layer RAG for retrieval-augmented responses. Knowledge engineering, graph database, embedding pipelines, retrieval tuning 9–15 months High value if knowledge is codifiable. Requires expert involvement
Domain Fine-Tuned Models Fine-tune foundation models on proprietary data and domain-specific tasks. Build defensible model assets. Training data curation, fine-tuning infrastructure, evaluation frameworks, versioning 6–12 months per model Higher investment but creates genuine IP. Needs quality data
Expert-in-the-Loop Systems Design systems where AI handles volume, experts handle exceptions and validation. Capture expert feedback to improve AI. Triage workflows, expert review interfaces, feedback capture, continuous learning loops 6–9 months Lower AI autonomy but higher trust. Sustainable path to full automation

2.4 Speed-to-Market Play — Execution Options

Execution Path Description Key Investments Timeline Risk Profile
Use Case Sprints Run time-boxed sprints attacking 2–3 high-value use cases. Prove value fast. Build momentum and learning. Cross-functional squad, rapid prototyping tools, lightweight governance, executive sponsorship 4–8 weeks per use case Fast learning. Risk of scattered efforts without consolidation
Managed AI Services Outsource AI capability to managed service providers. Focus internal effort on business integration and adoption. Vendor selection, SLAs, integration layer, internal change management 2–4 months to operational Fastest path. Limited differentiation. Dependency on vendor
AI Centre of Excellence (Lite) Stand up small CoE focused on governance, vendor management, and enablement. Let BUs experiment within guardrails. CoE team (2–4 people), governance framework, approved tool list, use case intake process 3–6 months to operational Balances speed with control. Scales organisational learning

3. Foundational Layer (Common to All Paths)

Before any of the four paths can succeed, a common foundation layer must be in place:

Foundation Area Description Why It Is Non-Negotiable Minimum Viable State
Data Accessibility Core business data is accessible, discoverable, and usable by AI systems Every path requires AI to access relevant data. No data access = no AI value. Key data sources identified, basic APIs or extraction available, data owners known
Identity & Access Management Clear controls over who (human and AI) can access what data and systems AI systems inherit access permissions. Without IAM clarity, you either block AI or create security/compliance risk. SSO in place, role-based access defined, service account governance established
Security & Privacy Baseline Policies and controls for how AI interacts with sensitive data, PII, and regulated information Regulatory exposure applies regardless of path. AI amplifies data risk. Data classification framework, DLP basics, AI-specific acceptable use policy
Governance & Accountability Clear ownership of AI initiatives, decisions, and outcomes Without governance, AI projects stall in committee or run wild without oversight. Executive sponsor identified, AI steering group defined, escalation path clear
Responsible AI Principles Articulated position on fairness, transparency, human oversight, and AI ethics Builds trust internally and externally. Prevents reactive scrambling when issues arise. Principles documented, high-risk use case criteria defined, review process established
Change Readiness Baseline organisational capacity to absorb new ways of working and human-AI collaboration AI fails more often from adoption failure than technical failure. Change impact assessment done, communication plan drafted, early adopters identified
Cost Visibility & Control Ability to track, allocate, and manage AI-related costs (API calls, compute, licensing) AI costs can spiral quickly. Without visibility, you cannot optimise or make informed decisions. Cost tracking mechanism in place, budget ownership clear, thresholds and alerts defined

3.1 Foundation Maturity Levels

Level Description Path Readiness
Level 0: Absent Foundation not addressed. Ad hoc or undefined. Not ready for any path. High risk of failure or stall.
Level 1: Emerging Foundation recognised. Initial policies or capabilities in place but inconsistent. Can attempt Speed-to-Market Play with guardrails. Other paths risky.
Level 2: Established Foundation codified and operational. Consistent application across most areas. Ready for Process Integration or Domain Moat plays. Platform Play possible with investment.
Level 3: Optimised Foundation mature, automated where possible, continuously improved. Enables scale. Ready for full Platform Play. Can run multiple paths concurrently.

3.2 Foundation Assessment Questions

Foundation Area Diagnostic Questions
Data Accessibility Can we list our top 10 data sources for AI? Can an AI system query them today? Do we know data quality issues?
Identity & Access Management Do we have service accounts for AI systems? Can we audit what AI accessed? Is access scoped appropriately?
Security & Privacy Baseline Do we know where PII lives? Do we have a policy on AI + sensitive data? Has legal/compliance reviewed AI use?
Governance & Accountability Who owns AI strategy? Who approves new AI use cases? Who is accountable if an AI system causes harm?
Responsible AI Principles Do we have documented AI principles? Do teams know what high-risk AI means here? Is there a review process?
Change Readiness Have we assessed workforce AI sentiment? Do we have change management capacity? Are leaders modelling AI use?
Cost Visibility & Control Can we track AI spend by project/team? Do we have budget thresholds? Do we understand unit economics?

Key takeaway: Sequencing matters. Start with strategic foundations (Economic Model + Strategic Positioning) to answer what is defensible and where the economics work. Then design capability and operating model based on those answers. This prevents the common mistake of starting with platform or use cases without understanding what the organisation is actually trying to become.
